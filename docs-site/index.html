EduTrack

Plataforma web de gestión integral de instituciones educativas: asistencia del personal, eventos y turnos, licencias médicas, estructura académica, biometría, sincronización con Moodle, reportes y analítica.

Next.js 14 Node 20 · Express Prisma · PostgreSQL 16 Keycloak · BFF Docker Compose Moodle
01

Visión general

EduTrack digitaliza la operación de un liceo: quién trabaja, cuándo, con qué grupo, y qué pasó con esa jornada. Combina un registro biométrico físico con una capa administrativa web.

🕐

Asistencia

Entradas/salidas del personal, tolerancias configurables, estados derivados (presente, tarde, salida temprana) e incidencias automáticas.

📅

Eventos & turnos

Clases, reuniones y jornadas con recurrencia, versionado temporal de series y suplencias docentes.

🏥

Licencias

Licencias médicas/laborales que justifican ausencias y se reconcilian con la asistencia.

🎓

Estructura académica

Ciclos lectivos, cursos, ofertas anuales, orientaciones, asignaturas y matrícula de estudiantes.

🔒

Biometría

Terminales ZKTeco (protocolo ADMS/iclock) que emiten marcas; vinculación segura persona↔dispositivo.

🔗

Moodle

Sincronización idempotente de usuarios, cursos e inscripciones vía servicios web REST.

📊

Reportes & analítica

Métricas de asistencia, rankings, exportaciones (PDF/CSV) y comparación entre ciclos.

🤖

Asistente NL→SQL

Preguntas en lenguaje natural que se resuelven con heurísticas curadas o traducción a SQL con LLM.

🔔

Notificaciones

Avisos in-app persistentes y Web Push (VAPID) para licencias, asignaciones e incidencias.

🌐

Producción: edutrack-uy.com  ·  Local: :3000 (frontend) / :4000 (API) / :8089 (Keycloak)

Anatomía del backend

El punto de entrada es backend/src/app.ts: arma la app Express, configura CORS (con variantes www. y api.), Helmet, morgan, métricas HTTP y monta cada router bajo su prefijo.

Orden de montaje (relevante)

El orden importa: los parsers especiales van antes del express.json() global.

  • /iclock → parser de texto plano para el protocolo ZKTeco ADMS (con reescritura de /cdata, /getrequest…).
  • /webhooks/didit → cuerpo raw para validar la firma HMAC.
  • Luego express.json() / urlencoded / cookieParser para el resto.
  • /auth/login tiene rateLimit propio (10 req/60s).
// backend/src/app.ts — montaje de routers
app.use("/iclock", iclockTextParser, zktecoIclockRoutes)
app.post("/webhooks/didit", express.raw(...), diditWebhookHandler)
app.use("/auth", keycloakAuthRoutes)   app.use("/auth", authRoutes)
app.use("/admin", adminRoutes)         app.use("/attendance", attendanceRoutes)
app.use("/events", eventsRoutes)        app.use("/courses", coursesRoutes)
app.use("/medical-leaves", ...)      app.use("/analytics", analyticsRoutes)
app.use("/biometric", ...)           app.use("/substitutions", ...)
app.get("/health", ...)   app.get("/ready", ...)  // readiness real

07

Servicios (lógica de negocio)

Los routers son delgados; la lógica vive en backend/src/services/ y en módulos de dominio. Muchos servicios están partidos en una función pura (testeable sin DB) y una capa con Prisma.

attendance/ & attendance-logic.ts

Cálculo de estado (PRESENT/LATE/EARLY_EXIT) según tolerancias; coverage-spans resuelve qué clases cubre una marca biométrica.

biometric-ingest-core.ts

Corazón de la ingesta biométrica: valida secreto del terminal, deduplica, ubica el evento asignado y crea la asistencia.

analytics/

metrics, rankings, planInstances, resolveInstances y resolveSubstituteInstances: expanden recurrencia y suplencias para calcular métricas.

events/

event-overlap (detección de solapes) y event-versioning (editar series a futuro sin reescribir el pasado).

substitutions.ts · substitution-occurrence.ts

Crea suplencias por ocurrencia y las resuelve contra la serie recurrente.

medicalLeaveReconciliation.ts

Cruza licencias aprobadas con las marcas: una licencia vigente convierte una ausencia en justificada.

school-year-service.ts

Resuelve el ciclo lectivo activo e impone invariantes (un solo ACTIVE).

query-assistant/

Asistente de consultas: heurísticas + parseo LLM + traducción NL→SQL validada. Ver flujo.

moodle.ts + integrations/moodle/

Sincronización idempotente (outbox + reconciliación). Ver Moodle.

audit-log.ts

Registro append-only (RF-11) de acciones sensibles: login, cambios de usuario, licencias, suplencias, biometría.

webPush.ts · notifications/email.ts

Envío de Web Push (VAPID) y correos (verificación, bienvenida de estudiante a Moodle).

non-working-days.ts

Feriados/días no laborables que excluyen ocurrencias del cálculo de ausencias.

Autenticación — Keycloak + BFF

El navegador nunca almacena tokens OIDC. El backend inicia el flujo, guarda los tokens en Redis y entrega al navegador solo la cookie sid (HttpOnly).

  1. Redirección

    El frontend redirige a GET /auth/login (backend).

  2. OIDC Authorization Code + PKCE

    El backend inicia el flujo contra Keycloak. Google OAuth y 2FA (TOTP) se configuran en Keycloak, no en la app.

  3. Callback

    Tras el callback, los tokens OIDC quedan en Redis; el navegador recibe la cookie HttpOnly sid.

  4. Sesión

    Cada request usa sid → el middleware resuelve la sesión desde Redis (auth/session-store.ts).

  5. Registro & perfil

    Registro, verificación de email y perfil siguen en /auth/*; las contraseñas viven en Keycloak.

Componentes: keycloak/ (realm + tema), auth/keycloak.ts, routes/auth-keycloak.ts, auth/session-store.ts, middlewares/auth.ts.

🚑

Runbook: error oidc/EAI_AGAIN = el contenedor auth no resuelve keycloak/redis (split de red Docker). Recuperar con force-recreate de auth y web. Nunca usar --remove-orphans (borra Moodle). En mobile/Safari en loop → COOKIE_SAMESITE=none.

Flujo: registro de asistencia

La lógica pura vive en attendance/attendance-logic.ts (getAttendanceStatus), separada de la DB para poder testearla.

Marca (biométrica o manual)→ ¿Licencia aprobada?→ Compara con horario del evento→ Estado→ ¿Incidencia?

  1. Se recibe la marca

    POST /attendance/register (manual) o ingesta biométrica. Con type (CHECK_IN/CHECK_OUT) y hora real. El horario se normaliza a la zona institucional con config/app-timezone.ts (uruguayWallToUtc, parseEventTimeToUruguayHhMm).

  2. ¿Hay licencia aprobada que cubra el horario?

    findApprovedLicenseCoveringEventTime() (medicalLeaveReconciliation.ts) usa licenseCoversInstant(). Si cubre → estado ABSENT_JUSTIFIED.

  3. Se compara contra el horario del evento

    getAttendanceStatus() (attendance/attendance-logic.ts): CHECK_IN → minutesLate > lateTolerance ⇒ LATE, si no PRESENT. CHECK_OUT → minutesEarly > earlyExitTolerance ⇒ EARLY_EXIT, si no EXIT. Duplicados: getDuplicateAttendanceMessage().

  4. Persistencia con ciclo lectivo

    attendance-school-year.ts (attachResolvedSchoolYearToAttendanceWhere) fija schoolYearId (del evento o el ciclo activo vía getActiveSchoolYearId()) para segmentar el listado admin.

  5. Incidencias & justificación

    scanAndCreateTeacherNoShowIncidents() y resolveNoShowIncidentIfAny() (attendance-incidents.ts) generan/cierran AttendanceIncident. Un admin justifica con justifyAttendance() (attendance-justifications.ts) — lanza AttendanceJustificationError si es inválido — cambiando previousStatus → newStatus y registrando recordAuditEvent().

📐

Tolerancias configurables en SystemSettings: attendanceLateToleranceMinutes (5), attendanceEarlyExitToleranceMinutes (5), attendanceNoShowGraceMinutes (15), attendanceClassBridgeGapMinutes (60).

🧩

Las faltas son estado derivado, no filas. Las ausencias se calculan a partir de las ocurrencias planificadas (recurrencia expandida); pueden no existir como filas Attendance hasta que un admin las materializa.

14

Flujo: ingesta biométrica & vinculación

Terminales ZKTeco (F22) hablan el protocolo push ADMS/iclock (texto plano). El parser vive en integrations/zkteco/iclock-parser.ts y la ingesta en services/biometric-ingest-core.ts.

Ingesta de una marca — processBiometricIngest()

  1. El terminal hace POST a /iclock/*

    parseAttlogBody() (zkteco/iclock-parser.ts) interpreta el cuerpo de texto; attlogStatusToPunchType() mapea el tipo. El dispositivo se ubica por findBiometricDeviceByAdmsSn() o findBiometricDeviceByCode(), y se valida el secreto con isBiometricSecretValid() (hashBiometricSecret + timingSafeEqual) e IPs permitidas.

  2. Se crea un BiometricPunch

    Marca cruda con occurredAt, deviceUserId y payload. processStatus = PENDING. Deduplicación por ventana (biometricDuplicateWindowMinutes) y por índice único (deviceId, deviceUserId, occurredAt).

  3. Resolución de persona

    Se busca el BiometricUserMapping (deviceUserId → User). Sin mapping → estado UNIDENTIFIED_PUNCH. Si hay vinculación pendiente, tryCaptureBiometricLinkPunch() captura la marca (LINK_CAPTURED).

  4. Ubicación del evento

    resolveBiometricAttendanceLinkage() + coverage-spans.ts: fetchTeacherClassSlotsForUruguayDay() trae las clases del día, buildPresenceSpans() arma los tramos de presencia y coverageForOccurrence()/resolveOccurrenceOutcome() deciden qué clase cubre la marca (con earlyEntryWindowMinutes() de entrada anticipada).

  5. Creación de asistencia

Ejemplo real — getAttendanceStatus()

export function getAttendanceStatus(params: {
  type: 'CHECK_IN' | 'CHECK_OUT'; actualTime: Date
  startTime?: Date | null; endTime?: Date | null
  hasApprovedLicense: boolean; lateToleranceMinutes?: number
}): RegisterStatus {
  if (params.hasApprovedLicense) return 'ABSENT_JUSTIFIED'
  const tolerance = params.lateToleranceMinutes ?? 5
  if (params.type === 'CHECK_IN') {
    if (!params.startTime) return 'PRESENT'
    const minutesLate = Math.floor(
      (params.actualTime.getTime() - new Date(params.startTime).getTime()) / 60000)
    return minutesLate > tolerance ? 'LATE' : 'PRESENT'   // entrada
  }
  if (!params.endTime) return 'EXIT'
  const minutesEarly = Math.floor(
    (new Date(params.endTime).getTime() - params.actualTime.getTime()) / 60000)
  return minutesEarly > tolerance ? 'EARLY_EXIT' : 'EXIT'  // salida
}

Ejemplo real — deriveOccurrenceStatus()

El estado de una ocurrencia no se guarda: se deriva del estado base de la serie y del instante actual.

export function deriveOccurrenceStatus(baseStatus, occStartAt: Date, occEndAt: Date) {
  if (baseStatus === 'CANCELLED') return 'CANCELLED'
  if (baseStatus === 'EXPIRED')   return 'EXPIRED'
  const now = new Date()
  if (occEndAt <= now)                    return 'COMPLETED'
  if (occStartAt <= now && now < occEndAt) return 'IN_PROGRESS'
  return 'SCHEDULED'
}

Ejemplo real — requirePermission()

Middleware que resuelve el alcance efectivo del permiso y exige all cuando la operación lo requiere.

export function requirePermission(permissionCode: string, requiredScope?: "own" | "all") {
  return async (req, res, next) => {
    const u = (req as any).user
    const userId = u?.id ?? u?.sub
    if (!userId) return res.status(403).json({ message: "Prohibido" })
    const scope = await userPermissionScope(userId, permissionCode, u?.role)
    if (!scope || (requiredScope === "all" && scope !== "all")) {
      return res.status(403).json({ message: "Prohibido" })
    }
    next()
  }
}

Ejemplo real — isValidUruguayanCI()

Dígito verificador de la cédula uruguaya con pesos [2,9,8,7,6,3,4]. Una sola implementación para auth y admin.

export function computeCICheckDigit(base7: string) {
  const weights = [2, 9, 8, 7, 6, 3, 4]
  const sum = base7.padStart(7, "0").split("")
    .map((d, i) => parseInt(d, 10) * weights[i])
    .reduce((a, b) => a + b, 0)
  return (10 - (sum % 10)) % 10
}

export function isValidUruguayanCI(ci: string) {
  const digits = onlyDigits(ci)
  if (digits.length < 7 || digits.length > 8) return false
  const base = digits.slice(0, -1)
  return computeCICheckDigit(base) === parseInt(digits.slice(-1), 10)
}

Ejemplo real — validateReadOnlySql() (guardrail)

Antes de ejecutar el SQL generado por el LLM: solo SELECT, un único statement, sin comentarios ni palabras prohibidas, y únicamente tablas de la allowlist.

export function validateReadOnlySql(sql: string): string {
  const cleaned = stripTrailingSemicolon(sql)
  if (!/^select\b/i.test(cleaned)) throw new Error('…_NOT_SELECT')

  // se analiza el "esqueleto" sin literales, para no rechazar datos legítimos con ';' o '--'
  const skeleton = blankStringLiterals(cleaned)
  if (skeleton.includes(';')) throw new Error('…_MULTIPLE_STATEMENTS')
  if (skeleton.includes('--') || skeleton.includes('/*')) throw new Error('…_COMMENTS_FORBIDDEN')
  if (FORBIDDEN_SQL.test(skeleton)) throw new Error('…_FORBIDDEN_KEYWORD')

  const unknown = referencedTables(cleaned).filter((t) => !ALLOWED_TABLES.has(t))
  if (unknown.length > 0) throw new Error(`…_UNKNOWN_TABLE:${unknown}`)
  return cleaned
}

Verificación de identidad (liveness) opcional en el registro. Módulo: integrations/didit/.

  1. Se crea una LivenessSession

    El id se envía como vendor_data; puede ligarse a un email.

  2. El usuario realiza la prueba

    Estados: PENDING → IN_PROGRESS → APPROVED/DECLINED/EXPIRED…

  3. Webhook con HMAC

    POST /webhooks/didit (cuerpo raw). signature.ts valida la firma; register-verification-from-decision.ts aplica la decisión.

  4. Se marca livenessVerifiedAt

    En User, si el sistema exigía prueba de vida (livenessCheckEnabled en SystemSettings).

Integración ZKTeco (terminales)

Terminales biométricos F22 con protocolo push ADMS. El servidor expone endpoints /iclock/* que el terminal consulta periódicamente.

  • Reescritura de rutas: algunos F22 llaman /cdata, /getrequest, /registry, /devicecmd sin prefijo → app.ts los reescribe a /iclock/*.
  • Parser: integrations/zkteco/iclock-parser.ts interpreta el cuerpo de texto plano.
  • Identidad del terminal: por admsSerial (query SN) o code; secreto por secretHash e allowedIps.

Arranque & comandos

Arranque local

# 1. Copiar variables y levantar toda la infra
cp .env.compose.example .env
docker compose up -d --build

# URLs: web :3000 · API :4000 · Keycloak :8089
docker compose logs -f auth web keycloak
docker compose down

Backend

cd backend
npm run dev              # servidor con hot-reload (tsx watch)
npm run test             # vitest (unit)
npm run test:coverage    # genera coverage/lcov.info
npm run typecheck        # ./node_modules/.bin/tsc --noEmit (NO npx tsc)
npm run prisma:studio    # Prisma Studio en :5555
npm run seed:academic    # seeds: academic · teachers · demo · realistic…

Frontend

cd frontend/web
npm run dev
npm run test
npm run typecheck
npm run test:e2e         # Playwright
⚠️

En el backend, usar ./node_modules/.bin/tsc --noEmit, no npx tsc (npm puede resolver el paquete obsoleto tsc@2.0.4).

  • REDIS_URL — obligatorio para sesiones BFF.
  • KEYCLOAK_ISSUER_URL, KEYCLOAK_CLIENT_SECRET, KEYCLOAK_REDIRECT_URI.
  • FRONTEND_URL, NEXT_PUBLIC_API_URL.
  • Tras HTTPS: COOKIE_SECURE=true y URLs alineadas frontend/backend/Keycloak.
